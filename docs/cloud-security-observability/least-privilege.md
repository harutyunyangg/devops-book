# Least Privilege. Նվազագույն արտոնությունների սկզբունք

## Տեսություն

**Least Privilege**-ը (հայերեն՝ «նվազագույն արտոնությունների սկզբունք») տեղեկատվական անվտանգության հիմնարար սկզբունք է։ Այն նշանակում է, որ **ցանկացած օգտատեր, ծրագիր կամ գործընթաց պետք է ունենա միայն այն նվազագույն իրավունքներն ու մուտքերը, որոնք անհրաժեշտ են իր աշխատանքը կատարելու համար, և ոչ ավելին**։ NIST-ը (SP 800-171) այն սահմանում է այսպես. յուրաքանչյուր սուբյեկտին տրվում են միայն այն համակարգային թույլտվություններն ու ռեսուրսները, որոնք անհրաժեշտ են իր գործառույթն իրականացնելու համար։

Պարզ ասած. յուրաքանչյուրին տվեք միայն այնքան «բանալի», որքան իրականում անհրաժեշտ է, և ոչ մի ավելորդ բանալի մի տվեք։ Սա վերաբերում է ոչ միայն մարդկանց, այլև ծառայություններին ու գործընթացներին՝ նույնիսկ այն դեպքում, երբ դրանց օգտագործումը «իրավաչափ» է բիզնեսի տեսանկյունից։

### Ինչու է դա կարևոր

- **Նվազեցնում է հարձակման մակերեսը (attack surface)։** Որքան քիչ իրավունք ունի օգտատերը կամ գործընթացը, այնքան քիչ հնարավորություններ ունի սպառնալիքը։ Եթե հաքերը գողանա օգտատիրոջ գաղտնաբառը, նա կկարողանա կատարել միայն այն գործողությունները, որոնք թույլատրված են այդ օգտատիրոջը, ոչ թե ամբողջ համակարգը կործանել։
- **Սահմանափակում է blast radius-ը (վնասի տարածման գոտին)։** Նույնիսկ եթե սուբյեկտը դիտավորությամբ կամ սխալմամբ վնասակար գործողություն կատարի, վնասը սահմանափակվում է հենց նրա թույլտվությունների շրջանակով։
- **Նվազեցնում է սխալների ազդեցությունը։** Եթե ծրագիրը «բագ» ունի, այն չի կարող փոխել կամ ջնջել այն, ինչին մուտք չունի։
- **Օգնում է համապատասխանությանը (compliance)։** Շատ ստանդարտներ (օրինակ՝ GDPR, ISO 27001) և պետական պահանջներ (օր.՝ NIST SP 800-171) պահանջում են մուտքերի սահմանափակում ըստ սկզբունքի։

### Հակառակ սկզբունքը՝ Privilege Creep

**Privilege Creep**-ը (արտոնությունների «սողացող» կուտակում) հակառակ երևույթն է. երբ ժամանակի ընթացքում օգտատերերը կուտակում են ավելի ու ավելի շատ իրավունքներ (օրինակ՝ պաշտոն փոխելիս, առանց հին իրավունքները հանելու), և ոչ ոք չի վերանայում դրանք։ Սա հենց այն է, ինչից խուսափում է least privilege-ը։ Հատուկ դեպք է **Privilege Escalation**-ը (արտոնությունների բարձրացում), երբ հարձակվողը օգտվում է չափազանց լայն իրավունքներից՝ ավելի բարձր մակարդակի մուտք ստանալու համար, որը հաճախ հենց privilege creep-ի հետևանք է։

### Կիրառման ոլորտներ

- **Օպերացիոն համակարգերում.** Օգտատերերի իրավունքներ, file permissions, processes. Ծառայությունները գործարկվում են non-root օգտատիրոջ տակ, ոչ թե ադմինիստրատորով։
- **Տվյալների բազաներում.** Կարդալ (read), գրել (write), ջնջել (delete) առանձին իրավունքներ. application-ը չի օգտագործում `db_owner`/`sa` մակարդակի հաշիվ (OWASP-ն ուղղակի խորհուրդ է տալիս այդպես)։
- **Cloud միջավայրերում.** IAM (Identity and Access Management)՝ գլոբալ ադմին իրավունքների փոխարեն՝ թե՛ աշխատակիցների, թե՛ ծառայությունների համար նվազագույն scope-ներ, roles և policies (օր.՝ AWS, Kubernetes RBAC)։
- **Ծրագրային ապահովման մշակման մեջ.** Microservices-ում յուրաքանչյուր ծառայություն ունի իր սեփական, սահմանափակ մուտքը, ոչ թե բոլորը կիսում են մեկ հզոր հաշիվ։ Ֆայլերը (credentials) տրվում են միայն այն ծառայությանը, որն իրականում պետք է դրանք պահի։
- **Նվազագույն արտոնությունների սկզբունքը.** Յուրաքանչյուր սուբյեկտի ամեն գործողությունը կատարվում է նվազագույն իրավունքներով, իսկ հատուկ մուտքերի կարիքի դեպքում տրվում է ժամանակավոր, ըստ scope-ի մուտք (JIT)։

| Հրաման | Նպատակ | Սպասվող արդյունք | Անվտանգության ռիսկ |
| --- | --- | --- | --- |
| `ls -l <path>` | Դիտել ֆայլի սեփականատիրոջը, խումբը և իրավունքները (rwx) | Իրավունքների ցուցակ | Անվտանգ, միայն կարդում է |
| `chmod 640 <file>` | Իրավունքներ հատկացնել owner-ին rw, group-ին r, մյուսներին՝ ոչինչ | Ֆայլի իրավունքների փոփոխություն | Կարող է կտրել մուտքը. ստուգեք owner/group-ը |
| `umask 077` | Լռելյայն սահմանափակել նոր ֆայլերի իրավունքները (միայն owner-ը) | Նոր ֆայլերի լռելյայն 0600 | Անվտանգ, բայց կարող է խանգարել shared workflows-ին |
| `useradd -M -s /usr/sbin/nologin <svc>` | Ստեղծել ծառայության օգտատեր առանց login shell-ի | Ոչ ինտերակտիվ օգտատեր | Անվտանգ, եթե shell-ը հենց `/usr/sbin/nologin` է |
| `visudo` | Խմբագրել sudoers-ը, ապահով syntax-ստուգմամբ | Խմբի/օգտատիրոջ սահմանափակ հրամանների ցուցակ | Սխալ շարահյուսությունը կարող է կոտրել sudo-ն |
| `setcap 'cap_net_bind_service=+ep' <binary>` | Տալ ծրագրին միայն մեկ հատուկ հնարավորություն (օր.՝ 80-րդ պորտ կապել)՝ ամբողջ root-ի փոխարեն | Root-ից ցածր, նեղ իրավունք | Զգույշ. setcap-ը կարող է փոխել ծրագրի վարքը |
| `getcap <binary>` | Ցույց տալ ֆայլի setcap-հնարավորությունները | Ընթացիկ capabilities | Անվտանգ |
| `setpriv --reuid=<uid> --regid=<gid> --clear-groups <cmd>` | Գործարկել գործընթացը կրճատված իրավունքներով | Ծրագիրը աշխատում է non-root-ով | Զգույշ. համոզվեք, որ ծրագիրը կարող է աշխատել առանց root-ի |
| `systemctl` + `User=` | systemd-ում ծառայությունը գործարկել որպես սովորական օգտատեր | Service-ը չի աշխատում root-ով | Անվտանգ, best practice |
| `usermod -aG <group> <user>` | Օգտատիրոջը ավելացնել խումբ (և միայն այդ խումբը) | Խմբային մուտք | Հետևեք, որ `-a`-ն կա, հակառակ դեպքում առկա խմբերը կջնջվեն |
| `last`, `lastlog`, `journalctl -u <svc>` | Վերանայել, թե ով և երբ է մուտք գործել | Մուտքի աուդիտ | Անվտանգ, կարդալու համար |

## Փորձարկում (Lab)

Միջավայր. սովորական Ubuntu/Debian Linux VM կամ Docker container (ոչ production)։ Թիրախն է ցույց տալ, որ ծառայությունը 80-րդ պորտ կապելու համար ամբողջ root-ի փոխարեն ստանում է միայն մեկ capability, իսկ sudo-ն սահմանափակվում է մեկ հրամանով։

```bash
# 1. Ստեղծենք ծառայության օգտատեր առանց login shell-ի
sudo useradd -M -s /usr/sbin/nologin app-svc
id app-svc

# 2. Փորձ՝ նորմալ օգտատիրոջը 80-րդ պորտ թույլ չի
#    (փոքր Python http server, ավարտել Ctrl+C-ով)
python3 -m http.server 80
#    սխալ՝ "PermissionError: [Errno 13] Permission denied"

# 3. setcap-ով թույլ տանք միայն 80-րդ պորտ կապելը
sudo setcap 'cap_net_bind_service=+ep' /usr/bin/python3
getcap /usr/bin/python3
python3 -m http.server 80
#    այժմ աշխատում է — բայց ծրագրի մնացած իրավունքը մնում է սահմանափակ

# 4. Մաքրենք capability-ն, երբ այլևս չի պետք
sudo setcap -r /usr/bin/python3
getcap /usr/bin/python3   # դատարկ

# 5. sudoers-ում սահմանափակենք՝ օգտատիրոջը թույլ տալ միայն systemctl
sudo visudo -f /etc/sudoers.d/lab
#    ավելացրեք՝   labuser ALL=(root) /usr/bin/systemctl
```

! Best Practices
    - Ծառայությունները միշտ գործարկեք non-root օգտատիրոջ տակ (systemd-ի `User=`)։
    - DB-ի application-հաշիվը չպահեք `db_owner`/`sa`-ով. տվեք միայն անհրաժեշտ read/write-ը։
    - Cloud-ում ադմին գլոբալ ռոլորների փոխարեն նախապատվեք scope-ով պայմանավորված, ժամանակավոր (JIT) մուտքերին։
    - setuid/setcap-ը կիրառեք որպես բացառություն, փաստաթղթավորեք դրանց գոյությունը և պարբերաբար աուդիտ արեք (`getcap -r /` ցուցակով)։
    - Պարբերաբար վերանայեք sudoers-ը, խմբերը և IAM-ի policies-ը՝ privilege creep-ը կանգնեցնելու համար։

Սպասվող արդյունք. սովորական օգտատիրոջը 80-րդ պորտ չի հաջողվում, setcap-ից հետո՝ հաջողվում է, իսկ sudo-ն սահմանափակվում է միայն `systemctl`-ով. բոլոր փորձերը անվտանգ են VM/container-ի սահմաններում և չեն դիպչում production-ին։

## Իրական DevOps իրավիճակ

### Ախտանիշ

CI/CD pipeline-ը կամ monitoring-agent-ը «կոտրվում» է, իսկ օպերատորը «լուծելու» համար ամեն ինչի թույլտվություն է ավելացնում. օրինակ` JSON ֆայլ կարդալու համար տալիս է ամբողջական `sudo` մուտք կամ Cloud-ում ավելացնում է `admin` ռոլոը խմբին։ Եվս մի քանի շաբաթ անց պարզվում է, որ շատ հաշիվներ ունեն շատ ավելի լայն իրավունքներ, քան բիզնեսին անհրաժեշտ է։ Սա դասական privilege creep-ի նախանշան է. անվտանգության աուդիտը (օր.՝ NIST SP 800-171-ի պահանջով) հայտնաբերում է չափազանց առատ թույլտվություններ, որոնց միջոցով հարձակվողը կարող է հասնել զգայուն տվյալների։

### Ախտորոշում

1. Security աուդիտի հաշվետվություն՝ «շատ հաշիվներ արտոնյալ (privileged) ռոլոր ունեն»։
2. Գործնական ստուգում. թիմը «խրվում» է այդ հաշվի փակ հրամանում, բայց աուդիտը ցույց է տալիս, որ մոռացված, ավելի հին հաշիվը դեռ ունի հզոր իրավունքներ։
3. Բաղադրիչների վերանայում. `sudo -l`, `groups`, `getcap -r /`, Cloud-ի IAM-ի ռոլորների ցուցակ, DB-ի grants. երևում է մեծ տարբերություն «ինչ պետք է» և «ինչ իրականում կա» միջև։

### Լուծում

- Յուրաքանչյուր գործողության համար որոշեք «նվազագույն բավարարությունը» և կիրառեք RBAC. իրավունքներն ու դերերը խմբավորեք ըստ փաստացի աշխատանքային պահանջի։
- Սահմանափակեք sudo-ն ըստ հրամանի` `/etc/sudoers.d/`-ում նշեք միայն անհրաժեշտ հրամանները, ոչ թե ամեն ինչ։
- Ծառայություններին տվեք setcap/`User=`-ով նեղ իրավունքներ, իսկ Cloud-ում ստեղծեք ժամանակավոր (JIT) մուտքեր՝ ըստ ժամանակի և scope-ի։
- Ջնջեք կամ ապաակտիվացրեք մոռացված հաշիվները, և հանեք «միայն մոռացության պատճառով» մնացած հզոր ռոլորները։

### Կանխարգելում

- Պարբերաբար վերանայեք իրավունքները (quarterly access review) և նշեք՝ յուրաքանչյուրը ինչու ունի յուրաքանչյուր մուտքը։
- Կիրառեք **Just-In-Time (JIT)** մուտքեր. իրավունք տվեք միայն անհրաժեշտ ժամանակահատվածի համար՝ ավտոմատ ավարտվող (օր.՝ 30 րոպե)։
- Օգտագործեք **RBAC** և, հաջորդ քայլում, **ABAC**՝ դերերով, ապա ատրիբուտներով (ժամանակ, վայր, սարք) պայմանավորված մուտքեր։
- Կազմեք աուդիտ և alerting. «ինչ կա» vs «ինչ պետք է» անհամապատասխանության դեպքում alert ստացեք՝ նախքան այն դառնա հարձակման ուղի։

## Հարցազրույցի հարցեր և պատասխաններ

### Ի՞նչ է least privilege-ը և ինչո՞ւ է այն կարևոր (mid-level)

Least privilege (կամ principle of least privilege) սկզբունքն է, որ յուրաքանչյուր օգտատեր, ծրագիր կամ գործընթաց ստանում է միայն իր աշխատանքը կատարելու համար անհրաժեշտ նվազագույն իրավունքներն ու մուտքերը, ոչ ավելին (NIST SP 800-171)։ Այն կարևոր է, որովհետև սահմանափակում է attack surface-ը և blast radius-ը. եթե ինչ-որ մեկի իրավունքները գողանում են կամ չարաշահվում, վնասը մնում է նվազագույն, բացի այդ պաշտպանում է սխալներից ու օգնում compliance-ին (ISO 27001, GDPR)։ Հակառակ երևույթը privilege creep-ն է՝ ժամանակի ընթացքում կուտակվող, չվերանայվող ավելորդ իրավունքները։

### Ինչպե՞ս կգործարկեիք least privilege-ը ամբողջական cloud ենթակառուցվածքում (senior-level)

Կսկսեի RBAC/ABAC-ով` դերեր և policies ըստ աշխատանքային ֆունկցիաների, և յուրաքանչյուր սուբյեկտին (մարդ, service, workload) կտայի միայն անհրաժեշտ scope-ներն ու permissions-ը, ոչ թե ադմին ռոլոր. սա NIST-ի «minimum necessary» սկզբունքն է։ Բոլոր արտոնյալ մուտքերը կդարձնեի Just-In-Time` ժամանակավոր, ավտոմատ ավարտվող sessions, ոչ persistent ադմին մուտք. իսկ ծառայությունները կգործարկեի non-root օգտատիրոջ տակ` DB-ի application-հաշիվները պահելով առանց `db_owner`-ի, իսկ նեղ մուտքերի համար կիրառեի capabilities (setcap) կամ OS-ի MAC (SELinux/AppArmor)։ Ամեն ինչ կուղեկցեի ավտոմատ աուդիտով ու alerting-ով, որպեսզի «ինչ կա» vs «ինչ պետք է» տարբերությունը անհապաղ երևա, և պարբերական access review-ով՝ privilege creep-ը կանգնեցնելու համար. least privilege-ը կիրառվում է ոչ միայն մարդու, այլ ամեն սուբյեկտի և ամեն interface-ի մակարդակում։

## Ինքնաստուգում

1. Ի՞նչ է least privilege-ը և որո՞նք են դրա հիմնական առավելությունները (attack surface, blast radius, compliance)։
2. Ի՞նչ տարբերություն կա privilege creep-ի և privilege escalation-ի միջև, և ինչպե՞ս է դրանցից յուրաքանչյուրը կապված least privilege-ի հետ։
3. Ի՞նչ տարբերություն կա RBAC-ի, ABAC-ի և MAC-ի միջև, և ե՞րբ է յուրաքանչյուրը կիրառվում։
4. Ի՞նչ է JIT (Just-In-Time) մուտքը և ինչո՞ւ է այն նվազեցնում ռիսկը։
5. Ինչո՞ւ է service-ը root-ով աշխատեցնելը վտանգավոր, և ինչպե՞ս եք դա կանխում systemd-ում (`User=`)։
6. Ի՞նչ է setcap-ը և ինչպե՞ս է այն ավելի նեղ, քան ամբողջ root-ը (օր.՝ `cap_net_bind_service`)։
7. Ինչո՞ւ է application-ի DB-հաշիվը `db_owner`/`sa`-ով պահելը հակառակ least privilege-ին (OWASP-ի տեսանկյունից)։
8. Ի՞նչ հրամաններով կվերանայեիք օգտատերերի իրավունքները Linux-ում (`sudo -l`, `groups`, `getcap -r /`) և ի՞նչ կփնտրեիք դրանցում։
