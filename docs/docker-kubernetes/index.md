# Docker և Կոնտեյներներ

## Տեսություն

**Docker**-ը բաց կոդով հարթակ է, որը թույլ է տալիս հավելվածները փաթեթավորել, առաքել և գործարկել մեկուսացված միջավայրերում՝ **կոնտեյներներում (containers)**։ 

### Ի՞նչ խնդիր է լուծում Docker-ը (VM vs Container)
Նախկինում հավելվածը տեղական (local) համակարգչից սերվեր տեղափոխելիս հաճախ էր առաջանում «իմ համակարգչի վրա աշխատում էր, բայց սերվերի վրա չի աշխատում» խնդիրը։ Սա պայմանավորված էր տարբեր օպերացիոն համակարգերով, գրադարանների այլ տարբերակներով և կոնֆիգուրացիաներով։

- **Virtual Machines (VMs):** Յուրաքանչյուր VM իր հետ բերում է ամբողջական Guest OS, որը պահանջում է սեփական kernel, RAM, CPU և մեծ ծավալ սկավառակի վրա (GB-ներ)։ Սա դանդաղեցնում է գործարկումը և սահմանափակում ռեսուրսների արդյունավետ օգտագործումը։
- **Containers:** Կոնտեյներները կիսում են Host (մայր) համակարգչի OS kernel-ը։ Դրանք չափազանց թեթև են (MB-ներ), միանում են ակնթարթորեն և ապահովում են գրեթե նույնանման մեկուսացում Linux-ի ներքին տեխնոլոգիաների շնորհիվ (Namespaces և Control Groups (cgroups))։

### Հիմնական հասկացություններ

- **Dockerfile:** Պարզ տեքստային ֆայլ է, որտեղ տրված են հրահանգները (բաղադրատոմսը)՝ Docker image-ը հավաքելու համար։
- **Image (Պատկեր):** Read-only snapshot է, որը պարունակում է հավելվածի աշխատանքի համար անհրաժեշտ բոլոր ֆայլերը, գրադարանները, կոդը և runtime-ը։
- **Container (Կոնտեյներ):** Image-ի գործարկվող, մեկուսացված օրինակն է։
- **Docker Registry (օր.՝ Docker Hub):** Պահոց է, որտեղ տեղադրվում և պահպանվում են պատրաստի image-ները՝ համատեղ օգտագործման համար։

### Dangling vs Unused Images
DevOps ինժեների համար կարևոր է տարբերակել այս երկու հասկացությունները՝ սկավառակի տարածքը արդյունավետ կառավարելու համար.

- **Dangling Images (Կախված):** Սրանք այն պատկերներն են, որոնք այլևս չունեն անուն կամ պիտակ (tag)։ Սովորաբար առաջանում են, երբ build եք անում պատկերի նոր տարբերակը նույն թեգով, և հին պատկերը մնում է որպես `<none>:<none>`:
    - *Մաքրում:* `docker image prune`
- **Unused Images (Չօգտագործվող):** Սրանք այն պատկերներն են, որոնք տվյալ պահին չեն օգտագործվում ոչ մի (ոչ ակտիվ, ոչ էլ կանգնեցված) կոնտեյների կողմից։ Դրանք կարող են ունենալ անուն և թեգ, բայց պարզապես ոչ մի տեղ կցված չլինել։
    - *Մաքրում:* `docker image prune -a` (ջնջում է բոլոր չօգտագործվողները, ներառյալ dangling-ները)։

## Հիմնական հրամաններ

| Հրաման | Նպատակ | Զգուշացում |
| --- | --- | --- |
| `docker build -t <name> .` | Ստեղծում է նոր Image տվյալ թղթապանակից | Սխալ context փոխանցելը կարող է դանդաղեցնել build-ը |
| `docker run -d -p 8080:80 --name <container_name> <image>` | Գործարկում է կոնտեյները background-ում | Պորտերի բախումից խուսափելու համար ստուգեք ազատ պորտերը |
| `docker ps` | Ցույց է տալիս ակտիվ (աշխատող) կոնտեյներները | Ցույց չի տալիս կանգնեցվածները (օգտագործեք `docker ps -a`) |
| `docker stop <container_id/name>` | Ուղարկում է `SIGTERM` և կանգնեցնում կոնտեյները | Եթե չի պատասխանում, 10 վայրկյանից կանցնի `SIGKILL`-ի |
| `docker rm <container_id/name>` | Ջնջում է կանգնեցված կոնտեյները | Չի ջնջում կոնտեյների հետ կապված volume-ները |
| `docker rmi <image_id/name>` | Ջնջում է Docker Image-ը | Չեք կարող ջնջել image-ը, եթե կա դրանից ստեղծված կոնտեյներ |
| `docker logs -f <container_name>` | Stream է անում կոնտեյների լոգերը | Շատ մեծ լոգերի դեպքում կարող է ծանրաբեռնել տերմինալը |
| `docker exec -it <container_name> sh` | Մուտք է գործում աշխատող կոնտեյների տերմինալ | Փոփոխությունները կորչում են կոնտեյները ջնջելիս |

## Փորձարկում (Lab)

Այս լաբորատոր փորձում մենք կստեղծենք պարզ հավելված `slang.js` անունով և կգործարկենք այն Docker կոնտեյների ներսում։

### Քայլ 1. Ստեղծել նախագծի ֆայլերը
Ստեղծեք նոր թղթապանակ և դրա մեջ `slang.js` ֆայլը հետևյալ պարունակությամբ.

```javascript
// slang.js
const http = require('http');
const server = http.createServer((req, res) => {
    res.writeHead(200, {'Content-Type': 'text/plain'});
    res.end('Բարև Docker-ի աշխարհից! Slang-ը պատրաստ է:\n');
});
server.listen(3000, () => {
    console.log('Server is running on port 3000');
});
```

Նույն թղթապանակում ստեղծեք `Dockerfile` (առանց որևէ ընդլայնման).

```dockerfile
# Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY slang.js .
EXPOSE 3000
CMD ["node", "slang.js"]
```

### Քայլ 2. Image-ի build և Container-ի գործարկում

Գործարկեք հետևյալ հրամանները Ձեր համակարգում.

```bash
lc-root:~$ docker build -t slang-app:v1 .
lc-root:~$ docker run -d -p 8080:3000 --name slang-container slang-app:v1
```

### Քայլ 3. Արդյունքի ստուգում

Ստուգեք հավելվածի աշխատանքը հարցում կատարելով.

```bash
lc-root:~$ curl http://localhost:8080
```

**Սպասվող արդյունք:**
```text
Բարև Docker-ի աշխարհից! Slang-ը պատրաստ է:
```

Կոնտեյների լոգերը տեսնելու համար՝
```bash
lc-root:~$ docker logs slang-container
```

Մաքրելու համար՝
```bash
lc-root:~$ docker stop slang-container
lc-root:~$ docker rm slang-container
```

!!! warning "Անվտանգության կանոն"
    Dockerfile-երում երբեք մի օգտագործեք `latest` tag-ը (օր.՝ `node:latest`) production-ի համար։ Դա կարող է բերել անկանխատեսելի փոփոխությունների հավելվածի վերագործարկման ժամանակ։ Միշտ նշեք կոնկրետ տարբերակը (օր.՝ `node:18-alpine`):

## Իրական DevOps իրավիճակ

### Ախտանիշ

Սերվերի վրա ազատ տարածությունը (Disk Space) սպառվել է (100% full): Բոլոր ծառայությունները կանգնել են, իսկ Docker-ի լոգերում հայտնվում է `No space left on device` սխալը։

### Ախտորոշում

1. Ստուգեք սկավառակի ընդհանուր վիճակը.
   ```bash
   lc-root:~$ df -h
   ```
2. Օգտագործեք Docker-ի ներկառուցված վերլուծիչը՝ հասկանալու համար, թե ինչն է խլում տարածքը.
   ```bash
   lc-root:~$ docker system df
   ```
   Սա ցույց կտա, թե որքան տարածք են զբաղեցնում Images-ները, Containers-ները և Volumes-ները։
3. Հաճախ խնդիրը **dangling** (չպիտակավորված) image-ներն են կամ հսկայական չափերի հասնող container լոգերը։

### Լուծում

1. Ջնջեք բոլոր **dangling** պատկերները.
   ```bash
   lc-root:~$ docker image prune
   ```
2. Եթե ավելի արմատական մաքրման կարիք կա, ջնջեք բոլոր **unused** (չօգտագործվող) կոնտեյներները, ցանցերը և պատկերները.
   ```bash
   lc-root:~$ docker system prune -a
   ```
   !!! warning "Զգուշացում"
       `docker system prune -a` հրամանը կջնջի բոլոր կանգնեցված կոնտեյներները և բոլոր այն պատկերները, որոնք կցված չեն որևէ կոնտեյների (նույնիսկ եթե դրանք ունեն անուն)։ 
3. Եթե խնդիրը volume-ների մեջ է, և դուք ունեք չօգտագործվող volume-ներ, ավելացրեք `--volumes` դրոշակը.
   ```bash
   lc-root:~$ docker system prune -a --volumes
   ```

### Կանխարգելում

- **Log Rotation-ի սահմանում:** Կոնֆիգուրացրեք `/etc/docker/daemon.json` ֆայլը՝ սահմանափակելու համար լոգերի առավելագույն չափսը.
  ```json
  {
    "log-driver": "json-file",
    "log-opts": {
      "max-size": "10m",
      "max-file": "3"
    }
  }
  ```
- **CI/CD Cleanup:** Ձեր CI/CD pipeline-երում ավելացրեք պարբերական մաքրման քայլեր (`docker image prune -f`):
- **Monitoring:** Տեղադրեք alert-ներ սկավառակի 80% և 90% լցվածության դեպքում։

## Հարցազրույցի հարցեր և պատասխաններ

### Ի՞նչ տարբերություն կա Docker Image-ի և Container-ի միջև։

**Image**-ը ստատիկ, read-only template է, որը պարունակում է կոդը, գրադարանները և կոնֆիգուրացիաները։ **Container**-ը այդ image-ի ակտիվ, գործարկվող օրինակն է (runtime instance)՝ գրելու հնարավորություն ունեցող շերտով (writable layer)։

### Ի՞նչ է Multi-stage build-ը և ինչո՞ւ է այն կարևոր։

**Multi-stage build**-ը թույլ է տալիս մեկ Dockerfile-ի ներսում օգտագործել մի քանի `FROM` հրահանգ։ Սա հնարավորություն է տալիս ծրագրի հավաքման (build) փուլում օգտագործել մեծ գործիքներ (օր.՝ SDK-ներ, compilers), իսկ վերջնական image-ի մեջ տեղափոխել միայն արդյունքը (artifact) և թեթև runtime-ը։ Արդյունքում վերջնական պատկերը ստացվում է շատ ավելի փոքր և անվտանգ։

## Ինքնաստուգում

1. Ո՞րն է տարբերությունը `docker stop` և `docker kill` հրամանների միջև։
2. Ինչպե՞ս կարող ենք կոնտեյների ներսի տվյալները պահպանել (persist) կոնտեյների ջնջվելուց հետո։
3. Ի՞նչ նպատակի է ծառայում `.dockerignore` ֆայլը։
4. Ինչու՞ է խորհուրդ տրվում չօգտագործել `root` օգտատերը կոնտեյների ներսում հավելված գործարկելիս։

## Հաջորդ քայլեր

Հաջորդիվ մենք կուսումնասիրենք, թե ինչպես միավորել մի քանի կոնտեյներներ `Docker Compose`-ի միջոցով և ինչպես է իրականացվում կոնտեյներների կառավարումը մեծ մասշտաբներում **Kubernetes (K8s)**-ի օգնությամբ։
